# Threat Model - Milestone 0006 Task 02.0 Storage path unification - 2026-11-14

Design-time (pre-implementation) STRIDE review of the 15 subtask specs in
`docs/roadmap/0006-unified-command-model-and-tui/02.0-storage-path-unification/`,
plan.md "Shared contracts" C3/C4/C5/C10/C11, decision-log D12, and the existing
code the task re-wires (`legacy_adapters.hpp`, `storage_factory.hpp`,
`storage_config.hpp`, `link_repository.hpp`, `redirect_handlers.cpp`,
`main.cpp`, `cli_parser.cpp`, `core/utils.cpp`). No 02.0 product code exists yet;
every requirement is phrased so an implementation briefing and `testing-expert`
can turn it into an assertion. T-IDs start at T-30 to avoid colliding with the
01.0 model's T-01..T-22.

Scope note: this task moves the live redirect/REST/CLI paths onto one configured
`app::ILinkStore` selectable with `--storage-config`, adds a process-local
full-`Link` L1 cache, a `Link<->LinkRecord` codec that packs unsupported fields
into `attributes_json`, and write-behind redirect counters with a background
flusher thread. SSRF/URL validation, slug/tag/metadata validation and the error
vocabulary are owned by `LinkCommandService` upstream of the store and are
reviewed here only as an invariant that must not regress (T-40).

## Assets & trust boundaries

- **Storage config YAML (new ingress at startup):** path from `--storage-config`
  or `URL_SHORTENER_STORAGE_CONFIG`, loaded by `ParseStorageConfigFile`
  (`src/config/storage_config.cpp`). Holds **secrets** (`postgres_dsn`,
  `redis_address`) and the `sqlite_path`. Crosses: operator file -> parser ->
  `StorageConfig` -> `BuildStorageAdapters` -> a live DB/Redis connection. Parse
  errors surface to stderr (CLI) and logs (subtasks 11, 12).
- **SQLite database file on disk (new shared, persistent store):** written by
  the server process *and* by one-shot CLI processes against the same path.
  Contains every `target_url` plus packed `attributes_json` (tags, metadata,
  campaign - operator/user-supplied, potentially sensitive/PII), redirect
  counters, soft-delete markers. Created lazily by `EnsureBootstrapped` under the
  process umask. Trust boundary: any local actor who can read the file or the
  YAML sees all link targets and backend credentials.
- **Untrusted user input (unchanged surface, new sink):** target URLs, slugs,
  tags, metadata, campaign flow `Link -> link_record_codec -> attributes_json
  (property_tree JSON) -> SQL`. Percent-encoded by the codec (subtask 02).
- **Redirect hot path (C10):** `findBySlug` (L1 -> repo fallback) +
  `recordRedirect` (in-memory delta + L1 patch, no request-thread I/O). Shared,
  lock-free `app::LinkBackend::store()` atomic pointer. Background flusher thread
  owned by `RepositoryLinkStore`.
- **Cross-process consistency boundary:** one process's write becomes visible to
  another only after the L1 TTL (5 s default on persistent backends) and only as
  far as the shared DB and SQLite locking allow.
- **Secrets at risk:** `postgres_dsn` (user:password@host), `redis_address`,
  `sqlite_path`, and any of these reaching logs, stderr, exception `what()`, or
  process listings. Redaction: `::observability::redactSecretValue` (handles
  `password`/`secret`/`token`/`dsn`) and `summarize_storage_config` (names only).

## Findings

### [HIGH] T-32 recordRedirect refreshes the L1 TTL, so a deleted or disabled link keeps redirecting indefinitely under sustained traffic (Tampering / integrity of a safety control)
- Subtask(s): 01, 05 (surfaces in 14 step 6).
- Vector / evidence: `01-expiring-link-cache.md:108-109` (`set` unconditionally
  sets `stored_at = now`; "`set` after expiry refreshes `stored_at`") combined
  with `05-record-redirect-write-behind.md:85-87` (recordRedirect step 2: "apply
  the same +1 / timestamp to that copy and `m_l1->set(slug, copy)`. The L1 entry
  is **not** erased"). Every successful redirect re-`set`s the entry, resetting
  its `stored_at`. A continuously hit slug therefore never reaches the TTL, so
  the "staleness bounded by the 5 s TTL" guarantee (README decision 2;
  `14-...:30-31,60`) does not hold for a *hot* link.
- Impact: after a cross-process `link disable`/`link delete` (CLI, or a second
  server), the running server keeps seeing the stale L1 copy as active, returns
  302 to the (now disabled/deleted) target, and each 302 refreshes the entry -
  a self-perpetuating stale redirect that never expires while traffic continues.
  Deleting or disabling an abusive/phishing/malware link fails to take effect on
  the exact links that matter most (high traffic). Task 02.0's own acceptance
  test 14 step 6 (poll `GET /share-a` every 0.25 s until 410) would hang past its
  8 s bound and fail, which is concrete evidence of the defect.
- Mitigation (testable): `ExpiringLinkCache` MUST expose a patch-in-place
  operation that updates the stored `Link` **without** resetting `stored_at`
  (e.g. `bool patch(slug, mutatorfn)` or a `set` overload that preserves the
  existing insertion time); `recordRedirect` MUST use it instead of `set`, so the
  TTL is anchored to the load time, not the last redirect. Tests: with `ttl = 5 s`
  and `ManualClock`, `set` at t0, `recordRedirect` at t3, a read at t6 is a miss
  and re-reads the repository; a disabled/deleted record made visible in the repo
  becomes visible within `ttl` even under continuous `recordRedirect` calls
  (14 step 6 converges). Resolve in the 01 and 05 specs before implementation.

### [MEDIUM] T-30 SQLite DB and YAML config readable by other local users (Information disclosure, secrets/PII at rest)
- Subtask(s): 10, 11, 15.
- Vector / evidence: `10-...:71-72` ("stored verbatim ... no existence check, no
  canonicalization"); `10-...:142-144` and `15-...` defer file permissions to an
  operator-documented concern; `11-...` creates/opens the DB via the probe
  (`Exists`) with no permission handling; `storage_factory.cpp` opens the file
  under the process umask. The DB holds every `target_url` and packed
  tags/metadata; the YAML holds `postgres_dsn`/`redis_address`.
- Impact: on a shared host a default umask (0022/0644) leaves the link database
  and the credentials YAML world-readable; any local user reads all redirect
  targets, user metadata and the backend password/DSN.
- Mitigation (testable): subtask 15 MUST document that both the YAML and the
  SQLite file must be mode 0600 and owned by the service account, and that the
  YAML path is visible in process listings (prefer the env var for secrets-laden
  configs); subtask 11 MUST NOT widen permissions on an existing file and SHOULD
  create the SQLite file with restrictive permissions where the backend allows.
  Test: bootstrap does not chmod the DB world-readable; docs section
  "Selecting the file" states the 0600 requirement. (Path traversal/symlink is
  not an escalation here - the path is operator-supplied, not attacker-supplied -
  but the verbatim, un-canonicalized path is recorded as an accepted design.)

### [MEDIUM] T-31 Storage-config parse-error message passed through verbatim may leak a DSN/password (Information disclosure)
- Subtask(s): 11, 12.
- Vector / evidence: `11-...:97-102` - on a non-`BadFile` exception the bootstrap
  throws `"storage config: " + e.what()`, and `12-...:52-56` prints that
  `e.what()` to stderr (CLI) / logs it (server, `12-...:67`). `Require()` messages
  are field-name-only (verified, `storage_config.cpp:8-10,54-83` - e.g.
  "invalid metadata.backend: <name>", a non-secret backend name), **but**
  `ParseStorageConfigFile` calls `YAML::LoadFile` (`storage_config.cpp:96-98`) and
  yaml-cpp parser/`BadConversion` exceptions can include the offending scalar
  content; a malformed line adjacent to `postgres_dsn`/`redis_address` could put a
  credential into `e.what()`. The subtask-11 redaction test only covers
  `summarize_storage_config`, not the parse-error path.
- Impact: a DSN password or Redis address surfaces on stderr or in a log line,
  defeating the "never log DSNs/secrets" rule (CLAUDE.md; C6).
- Mitigation (testable): the generic-exception branch MUST NOT emit raw
  `e.what()`; map non-`BadFile` parse/validation failures to a fixed
  `"storage config: invalid configuration"` (or run `e.what()` through a scalar
  redactor that strips `password=`/`://user:pass@`/known-key values) while
  keeping the `Require` field-name messages. Test: a YAML whose
  `postgres_dsn`/`redis_address` holds a recognizable password token and is made
  to fail parsing (bad type, truncated) produces a stderr/log line containing
  neither the token, the host, nor the DSN.

### [MEDIUM] T-33 Write-behind counter loss and cross-process lost update (Tampering, Repudiation) - ACCEPTED/CARRIED
- *Amended 2026-11-14 after the 02.0/05 implementation review (user decision):*
  the R-1 window can revert a **safety field** (`enabled`, `deleted_at`), not
  just lose a delta - a disable or soft-delete inside the window is
  overwritten and the link redirects again until the next change. A hard
  delete is not resurrected (`UPDATE` matches 0 rows). Same-process races
  (flusher thread vs `update()`) are closed by a store write mutex; the
  cross-process window is accepted (D12, amended).
- Subtask(s): 05, 11, 14.
- Vector / evidence: `decision-log.md:88,115` (D12: approximate, timer-flushed,
  races R-1/R-2 accepted); `05-...:97-117,214-224` (R-2 transient under-read while
  a flush is mid-write; R-1 two processes flushing one slug lose a delta; crash
  between flushes loses up to `stats_flush_interval` of counts).
- Impact: `link.stats.total_redirects` is approximate and can regress or be lost;
  the flush is a read-modify-write of a *freshly read* record, so a delta written
  inside the fresh-read->`UpdateLink` window could still clobber a concurrent
  change (R-1). Not an authorization or data-exfil issue; an integrity/audit
  concern only if anyone treats these counters as authoritative (e.g. abuse
  throttling).
- Mitigation (testable): counters MUST be documented as display-only/approximate
  (README R-3, D12) and MUST NOT gate any security decision; the authoritative
  metric is `click_events`/analytics. The lost-update regression in
  `05-...:178-180` MUST assert that a flush never reverts a concurrent
  `enabled=false`/soft-delete (the flush writes only the stats attribute of a
  freshly read record). Accepted as designed; a repository-level atomic
  `IncrementCounter`/CAS to close R-1 is an architect decision for a later task.

### [MEDIUM] T-34 Shared-SQLite write contention ("database is locked") on concurrent server-flush + CLI write (DoS / availability)
- Subtask(s): 11, 14.
- Vector / evidence: `14-...:116-119` ("If SQLite reports `database is locked`
  ... that is a product finding (busy timeout configuration)"); the server's
  background flusher (`05-...:120-126`) writes on an interval while CLI processes
  write to the same file; `tests/unit/storage/sqlite/11_busy_timeout_configuration.cpp`
  exists but subtask 11 does not state that the bootstrap's `SqliteSessionFactory`
  sets a busy timeout / WAL mode.
- Impact: a CLI `link create/update` or a flusher write can fail immediately with
  "database is locked" when the other process holds the write lock, surfacing as
  `storage_failure` to the operator or a dropped (re-queued) counter flush;
  under load this is an availability regression of the new shared-file mode.
- Mitigation (testable): subtask 11 MUST ensure the SQLite sessions opened by
  `BuildStorageAdapters` apply a non-zero `busy_timeout` (and WAL where
  appropriate) so concurrent single-writer contention blocks-and-retries rather
  than hard-failing. Test (subtask 14): the server-running + CLI-write scenario
  completes without an unhandled "database is locked"; a flush failure is
  re-queued and persisted on the next interval (already in `05-...:183-184`).

### [MEDIUM] T-40 SSRF / URL validation must stay upstream of the re-pointed store (Tampering, SSRF) - INVARIANT TO GUARD
- Subtask(s): 04, 08, 09 (invariant), 02 (codec must not re-admit targets).
- Vector / evidence: SSRF/private-host rejection lives in
  `LinkCommandService::CreateLink` (`src/app/link_command_service.cpp:69`,
  `normalizeTargetUrl` -> `validateTargetUrl` -> `isPrivateHost`,
  `core/utils.cpp:237`) and in the update/`ReplaceLinkTarget` path, **before**
  `store_.create/update`. Subtasks 08/09 re-point only reads (`findBySlug`),
  `slugExists` and persistence; they do not add a create/update path. Risk: a
  future direct `store().create(link)` / `store().update(link)` call from a
  handler or CLI that bypasses `LinkCommandService` would persist an unvalidated
  (private-target / SSRF) URL.
- Impact: if any create/update path bypasses `LinkCommandService`, the
  `SHORTENER_ALLOW_PRIVATE_TARGETS` SSRF guard is defeated and private/internal
  targets become redirectable.
- Mitigation (testable): `RepositoryLinkStore::create/update` are persistence
  only; the sole create/update entry remains `LinkCommandService` (which
  validates). Regression test: with a `RepositoryLinkStore` installed, a REST/CLI
  `link create` of a private-target URL (`http://127.0.0.1/...`, `http://10.0.0.1`)
  is still rejected with `invalid_url` and nothing is persisted; a grep guard
  confirms no `src/http/**`/`src/cli/**` create/update path calls
  `store().create`/`store().update` directly. The codec (subtask 02) only maps
  an already-validated `Link`; it performs no URL re-admission.

### [MEDIUM] T-35 Repository outage renders every link as not-found instead of a 5xx (Availability / integrity) - ACCEPTED/DEFERRED (R-5)
- Subtask(s): 03.
- Vector / evidence: `03-...:81-85,161-163` - `findBySlug` returns
  `std::optional`, so a `transient_failure`/`permanent_failure` is logged
  (error-name only) and returned as `nullopt`; the redirect handler then produces
  404/410 rather than 503.
- Impact: during a DB blip every redirect looks deleted/absent; an actor who can
  induce repository errors makes all links vanish (no cache-poisoning, no data
  exposure - availability/integrity only). No worse than today's single-process
  behavior for the default path.
- Mitigation (testable): documented limitation (R-5); fix (a `Result`-carrying
  `findBySlug`) is deferred to Task 03.0 / an ADR. Test: a repository forced into
  `transient_failure` logs `link_store_read_failed` with the error name only
  (no target URL/tags) and caches nothing.

### [LOW] T-36 findById bounded full scan is a DoS amplifier on the admin path (DoS)
- Subtask(s): 03.
- Vector / evidence: `03-...:86-91,164-165` - no `GetById` on the port, so
  `findById` pages `ListLinks` up to `id_scan_max = 100000` records
  (`id_scan_page = 200`), decoding each, O(n), stopping only at the first match
  or the cap.
- Impact: an admin `link get --id <absent>` against a large DB scans up to 100k
  rows / 500 queries of DB I/O per call; repeated calls amplify load. Never on the
  redirect fast path; admin/`write`-gated.
- Mitigation (testable): the hard cap `id_scan_max` is enforced and tested
  (`03-...:133-135` "stops at `id_scan_max`"); `findById` is admin-only and never
  reached by redirects (grep/review). Add `GetById` to `::IMetadataRepository`
  (three adapters + contract suite) if admin usage shows it matters.

### [LOW] T-37 Attribute-packing codec: injection surface and unknown-schema-version handling (Tampering)
- Subtask(s): 02.
- Vector / evidence: `02-...:54-66,111-116,134-145` - user tags/metadata/campaign
  are packed into `attributes_json` via `boost::property_tree` with reserved
  `lnk_*` keys; values are percent-encoded; keys with `.` are forbidden (would be
  split/lost by property_tree). `02-...:180` leaves "readers must fail the read on
  higher `lnk_v` versions" as a deferred decision.
- Impact: (a) a crafted tag/metadata/campaign value aiming to break out of the
  JSON or forge a reserved `lnk_*` key; mitigated because values are
  percent-encoded and user metadata keys live *inside* the `lnk_meta` value (they
  cannot collide with top-level `lnk_*` keys), and property_tree escapes on
  serialize. (b) An unrecognized future `lnk_v` read with current logic could be
  misinterpreted (e.g. a record read as `enabled` when a newer version meant
  otherwise).
- Mitigation (testable): the real-SQL round-trip test (`02-...:136-138`), the
  hostile-value cases (`.`, `&`, `=`, `,`, `%`, `"`, `\`, newline, non-ASCII, 2 KB)
  and "only `lnk_*` keys produced on write" cover (a); for (b), `record_to_link`
  MUST fail-closed (`bad_attribute`) on an `lnk_v` it does not understand rather
  than silently trusting the `is_active`/`lnk_*` fields. Add that assertion to the
  02 spec. Codec never logs attribute values (`02-...:158`).

### [LOW] T-38 Configured ICacheStore (Redis) must never resolve links, only be invalidated (Tampering / cache poisoning) - INVARIANT
- Subtask(s): 03, 04.
- Vector / evidence: README decision 2 and `03-...:95-96,166-167` - for `Link`
  data the configured `ICacheStore` is **write-invalidate only** (`Delete`), never
  read; only the process-local `ExpiringLinkCache` (L1) answers reads. Honoring
  `cache.backend: redis` for link reads is explicitly deferred.
- Impact: if a later change ever read links from the shared `ICacheStore`, a
  poisoned/tampered Redis entry (Redis is non-authoritative/fail-open, possibly
  network-reachable) could redirect users to an attacker target. In this task
  that path does not exist, so there is no exposure; the risk is regression.
- Mitigation (testable): `RepositoryLinkStore::findBySlug`/`findById` MUST read
  only L1 then `IMetadataRepository`, never `ICacheStore::Get`; `ICacheStore` is
  touched only by `Delete` (invalidate). Test/grep: no `m_cache->Get` in the store;
  a poisoned entry in the fake `ICacheStore` does not change a `findBySlug`
  result. Deferring Redis link-reads (which needs `CacheValue` extension) is
  recorded as a risk, not shipped.

### [LOW] T-39 LinkBackend holder install/reset lifetime (UAF if reset at runtime) (Elevation / crash)
- Subtask(s): 07.
- Vector / evidence: `07-...:54-74,138-141` - `store()` is a lock-free atomic load;
  `reset()`/`install()` are documented "startup / tests only, not while redirect
  threads run"; the bundle holds a non-owning aliasing `shared_ptr` into the
  holder. The install-once rule is documented, not enforced on the read side.
- Impact: a future caller invoking `reset()`/`install()` while requests are in
  flight could free the store under a thread holding `ILinkStore&`, a
  use-after-free. Within this task all callers are startup/teardown.
- Mitigation (testable): the install-once-at-startup contract is documented in
  `link_backend.hpp`; the concurrency smoke test (`07-...:125-129`: 4 readers vs
  alternating install/reset, never null, no crash) stands; the non-owning bundle
  pointer is proven valid while the holder lives (`07-...:131`). Any later runtime
  swap (hot reload) MUST move to a `shared_ptr`-returning `store()` first.

### [LOW] T-41 URL_SHORTENER_STORAGE_CONFIG silently activates a persistent backend (Tampering / test hermeticity)
- Subtask(s): 10, 13.
- Vector / evidence: `10-...:58-60` (env fallback, flag overrides);
  `13-...` notes `run_cli` has no `env` parameter today, so CLI subprocesses
  inherit the caller's environment including a stray `URL_SHORTENER_STORAGE_CONFIG`.
- Impact: any server/CLI process inheriting the env var silently uses a persistent
  backend instead of the in-memory default; the isolation half of the CLI
  integration tests would be non-hermetic (false pass/fail) if the env leaks in.
- Mitigation (testable): subtask 13 adds `clean_env()` (drops the var) for the
  isolation cases and an explicit env for the persistence cases
  (`13-...` helpers); subtask 15 documents the precedence (flag > env > default).
  Test: the default-mode CLI tests pass with `clean_env()` regardless of the
  ambient environment.

## Verdict: PASS_WITH_FOLLOWUP

No CRITICAL finding, so this is **not** a merge BLOCK. The core design is sound:
SSRF/URL validation stays upstream in `LinkCommandService` (T-40 confirmed, not
regressed), the redirect fast path adds no request-thread repository I/O
(write-behind deltas + background flusher, C10), links are never resolved from
the shared Redis cache (T-38), secrets are redacted by
`summarize_storage_config`/`redactSecretValue`, and the codec round-trips through
the real SQL mapper. One HIGH design defect must be resolved in the specs
**before implementation** of the owning subtasks:

1. **T-32 (HIGH, spec defect in subtasks 01 + 05):** `recordRedirect` re-`set`s
   the L1 entry on every redirect, refreshing `stored_at` and defeating the TTL
   for hot links, so a cross-process `disable`/`delete` can keep redirecting
   indefinitely (and breaks acceptance test 14 step 6). Add a patch-in-place
   cache op that preserves `stored_at`; have `recordRedirect` use it. Resolve in
   the 01 and 05 specs first.

Required follow-ups before the owning subtasks start:

2. **T-31 (MEDIUM):** replace the verbatim `e.what()` passthrough in
   `InitLinkBackend`'s generic-exception branch with a fixed/redacted message;
   add a parse-error-with-DSN leak test (subtask 11/12).
3. **T-34 (MEDIUM):** confirm the bootstrap's SQLite sessions set a `busy_timeout`
   (+ WAL) so shared-file server+CLI writes block-and-retry instead of hard-
   failing (subtask 11, asserted in 14).
4. **T-30 (MEDIUM):** document the 0600 requirement for the SQLite file and the
   YAML, and ensure bootstrap does not widen permissions (subtasks 11, 15).
5. **T-37 (LOW):** make `record_to_link` fail-closed on an unknown `lnk_v`.

Carried/accepted as designed: T-33 (approximate write-behind counters, D12/R-1/
R-2), T-35 (outage-as-not-found, R-5), T-36 (findById bounded scan), T-38/T-40
(invariants to guard with tests, not new code), T-39 (install-once contract),
T-41 (env precedence + test `clean_env`).

Hand T-32/T-31/T-37 (and the T-40/T-38 regression guards) to `cpp-expert` and
the spec authors; hand every per-threat assertion to `testing-expert` for the
`app__*`, `storage__*` and `cli_*` suites.
