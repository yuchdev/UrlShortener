# Threat Model - Milestone 0006 Task 04.0 REST and CLI adapters - 2026-11-16

Design-time (pre-implementation) STRIDE review of the 15 subtask specs in
`docs/roadmap/0006-unified-command-model-and-tui/04.0-rest-and-cli-adapters/`,
plan.md "Shared contracts" C1-C11 (esp. C2/C3/C4/C5/C6/C7/C10), decision-log D4/D14,
the carried items for 04.0 in
`.claude/state/implement-milestone-0006-unified-command-model-and-tui.json`
(`milestone_carry_forward` 3/18/19/21/25/27, `cross_task_subtask_edges`), and the
user decisions in `status.md` "Notes & decisions" (2026-11-16). No 04.0 product
code exists yet; every requirement is phrased so an implementation briefing and
`testing-expert` can turn it into an assertion. T-IDs start at **T-60** to avoid
colliding with 01.0 (T-01..T-22), 02.0 (T-30..T-41) and 03.0 (T-50..T-59).

This task re-points the two existing transports (REST resource routes, CLI
`link <verb>`) at the 03.0 registry through one bridge, and adds the generic
surface: `GET /api/v1/links`, `POST /api/v1/commands`, `GET /api/v1/commands`
(all gated by `--command-api-enabled`, role from `--command-api-role`) and the
CLI `cmd <name>` one-shot. The registry itself (auth-before-validation, bounded
scanner, value-free errors, audit) is 01.0/03.0 and reviewed there; this review
is the **adapter trust boundary** - identity derivation, the gate, error/status
mapping, input ingress limits, argv handling, and the invariants the adapters
must not regress.

## Assets & trust boundaries

- **REST request (primary network boundary):** method/target/query/body/headers
  arrive from any client that can reach the TCP port. **Every acceptor binds
  `tcp::v4()`** (`http_server.cpp:116,135`, verified), i.e. all IPv4 interfaces -
  there is no bind-address restriction, so a loopback **peer-address** check is
  the only locality guard. Request-size hardening (`413` body, `414` target)
  runs in `http_session.cpp:59,151` before routing.
- **Caller identity (`CallerContext{principal, control_set, transport}`):**
  synthesized by the adapter and **fully trusted** by `execute` as the sole
  authorization root (01.0 T-11). REST resource routes = `Admin`/`rest-resource`
  (status quo, unauthenticated); gated routes = `command_api_caller` (role from
  config, `Admin` only for loopback peer); CLI = `Admin`/`local-operator`
  (`User` under `--read-only`). `principal`/`transport` flow **verbatim** into
  audit records and are **not** PII-redacted by the logger.
- **The config gate (`command_api_enabled`, `command_api_role`):** the whole
  access-control perimeter for all new HTTP surface until Milestone 0002 sessions
  exist. Default `false`/`user` is security-load-bearing.
- **Command-ingress JSON:** REST body (`POST /api/v1/commands`), REST query
  (`GET /api/v1/links`), CLI `--json`/stdin/`--arg`. All must reach the one
  bounded scanner (01.0/01) with the hardening limits (`max_bytes`, depth,
  members); `args` text is assembled only by `commands::args_builder` (01) /
  `coerce_args` (11), never concatenated.
- **Response/audit sinks crossing back out:** the envelope / legacy
  `{"error":{...}}` body, `X-Request-Id`, stdout, stderr, the audit log. Must
  carry no raw request body, no arg values, no exception/driver text, no secret,
  no PII, no unescaped control chars.
- **CLI argv / environment:** `--arg k=secret` and `--json '{...}'` are visible
  in process listings and shell history; `--storage-config` path and env.
- **Secrets at risk:** DSN/redis/sqlite path (via `system.info` over REST, via
  parse errors), analytics salt, TLS material, tokens passed as args, exception
  `what()`, hostile slugs/URLs/query in logs.

## Findings

### [HIGH] T-60 Resource routes remain fully unauthenticated and run as Admin (Spoofing/Elevation) - ACCEPTED/CARRIED (status quo)
- Subtask(s): 02 (03-06 inherit).
- Vector / evidence: `02-...:33-34,50` (`resource_route_caller()` = `Admin`,
  no `AccessGuard` anywhere in `src/http`, verified); listeners bind `tcp::v4()`
  (`http_server.cpp:116`), so any host that can reach the port creates/patches/
  deletes links as `Admin`.
- Impact: unauthenticated full write to the management plane. In absolute terms
  HIGH, but it is **pre-existing** (today's handlers already call
  `LinkCommandService` with no auth) and C3 forbids changing it here; this task
  only relabels the existing behavior as `Admin`/`rest-resource`.
- Mitigation (testable): documented as a deliberate status-quo carry-over in
  `command_bridge.cpp` and `docs/security/` (Task 08.0); real auth arrives in
  Milestone 0002. No new exposure is added. Test: `resource_route_caller()` is
  `Admin`/`rest-resource`/`rest`; the bridge adds no new open route (the only
  new routes are the gated ones). Not a merge blocker because it is unchanged
  behavior, but it MUST be called out in the PR and the operator guide.

### [HIGH] T-71 `GET /api/v1/links` lets an unauthenticated non-loopback `User` enumerate all links incl. soft-deleted (`status=all|deleted`), contradicting the 2026-11-16 user decision (Info disclosure, broken access control) - SPEC GAP
- Subtask(s): 07 (gate from 08).
- Vector / evidence: `07-...:30-33,71,95` route runs with
  `command_api_caller(config, peer)` = default `user` for any non-loopback peer,
  and `link.list` is `Permission::read` (03.0/14), so a non-loopback caller with
  no credential lists every link; the spec's own test asserts
  "`status=all` includes disabled/deleted/expired" and "enabled + default role
  from a non-loopback peer still lists". The USER decision (status.md
  2026-11-16; state `milestone_carry_forward[25]`) requires: `GET /api/v1/links`
  **requires an authenticated caller (401 otherwise)** and `status=all|deleted`
  **require write/admin**. The spec implements neither; as written it ships a
  full-slug + soft-deleted enumeration oracle to any client once the gate is on.
- Impact: once `--command-api-enabled true`, any network client enumerates all
  active links, and with `status=all|deleted` all disabled/soft-deleted ones -
  a reconnaissance oracle (slugs, targets, campaign/metadata) and a leak of
  links an operator believed deleted. CWE-200 / CWE-285 / OWASP A01.
- Mitigation (testable): amend spec 07 before implementation to honor the user
  decision. Concretely, until 0002 sessions exist the "authenticated caller" is
  the gated caller, so: (a) `status=all|deleted` MUST require write/admin -
  reject them for a `User` caller with `not_authorized` (403) and never return
  soft-deleted/disabled rows to a `User`; (b) record explicitly that the config
  gate is the stand-in for "authenticated" until 0002 and that a `User` caller
  is limited to `status=active` (default). This likely needs `link.list` to
  carry a `permission_for` hook that **raises** to `write` when
  `status in {all,deleted}` (01.0 T-09 pattern: hooks may only raise), enforced
  in `execute`. Brief `app-architect` to amend 07 (and possibly 03.0/14's
  descriptor). Tests: non-loopback `User` + `status=all` -> 403 `not_authorized`,
  store not enumerated; `User` + default -> only active rows; loopback `admin` +
  `status=all` -> full list.

### [HIGH] T-64 The config gate is the entire access-control perimeter; wrong default or peer check = open management API (Elevation)
- Subtask(s): 08 (consumed by 07, 09, 10).
- Vector / evidence: `08-...:33,43-48,56-72,105` (`command_api_enabled = false`,
  `command_api_role = "user"` defaults; `command_api_caller` returns `Admin`
  only when role is `admin` **and** `is_loopback_peer(peer)`; `std::nullopt`
  peer = non-loopback = `User`). Listeners bind all IPv4 (`08-...:66`), so the
  peer check is the only locality guard.
- Impact: if the default ever flips to `true`/`admin`, or `is_loopback_peer`
  mis-classifies a remote address as loopback, or an absent peer defaults to
  `Admin`, the full generic command API (incl. `db.rows`, `system.info`) opens
  to the network. CWE-1188 / CWE-285.
- Mitigation (testable): `ServerConfig{}.command_api_enabled == false` and
  `== "user"` asserted; `--command-api-role` accepts only `user|admin`
  (case-sensitive) else `std::invalid_argument`; neither flag read from env;
  `is_loopback_peer` true only for `127.0.0.0/8`, `::1`, `::ffff:127/104` and
  false for `10/8`,`192.168/16`,`::ffff:10.*`; `command_api_caller` with role
  `admin` + non-loopback or `nullopt` -> `User` (fail-closed). The default
  change requires security-auditor sign-off recorded in the PR (`08-...:105`).
  Tests: `24_command_api_caller` full matrix + defaults assertion.

### [MEDIUM] T-61 `manage_users` must be refused over REST for every role/peer (Elevation, defense-in-depth) - carries 01.0 T-11
- Subtask(s): 02 (`rest_policy_refusal`), 09 (applies it).
- Vector / evidence: `02-...:68-73,89,110` (`rest_policy_refusal` refuses a
  `manage_users` descriptor with `not_authorized` before `execute`, even for an
  `Admin` caller); `09-...:76,99` applies it before `execute`. D4: user
  management never crosses REST before 0002.
- Impact: without the transport rule, a loopback `admin` caller (or a future
  bug raising `control_set`) could invoke user-management commands over HTTP.
- Mitigation (testable): `rest_policy_refusal` returns a `not_authorized`
  envelope for any `manage_users` descriptor and the handler is never entered,
  for every role and peer; `read`/`write` descriptors -> `nullopt`. It is a
  transport rule, not a substitute for `execute`'s own check (C7). Test: stub
  `manage_users` descriptor -> 403 for `Admin`/`User`, loopback and remote,
  handler call-count 0.

### [MEDIUM] T-66 Generic endpoint exposes every registered command over HTTP when enabled (Info disclosure, Elevation)
- Subtask(s): 08, 09.
- Vector / evidence: `08-...:12-18,119-121`; `09-...:14,99` - `POST
  /api/v1/commands` reaches `db.rows`, `system.info`, import/export and (later)
  jobs. Read-only unless loopback+admin; off by default.
- Impact: once enabled, a read caller can run `db.rows`/`system.info` and list

  a mis-set gate is the whole catalog.
- Mitigation (testable): defaults off/user (T-64); `manage_users` refused
  (T-61); `db.*` is allowlist-only and `system.info` is secret-free by 03.0
  construction (T-51/T-53, re-guarded here); every error code maps to the
  01.0/02 HTTP status. Test (`22_...`): enabled+`user` -> `link.create` 403,
  `db.rows{"table":"users"}` 404 `not_found` (no name echo), `system.info` leaks
  no sentinel secret; enabled+loopback-admin -> full lifecycle works.

### [MEDIUM] T-67 Drive-by cross-origin POST to the local command API (CSRF) - mitigated by required JSON content type
- Subtask(s): 09.
- Vector / evidence: `09-...:26-27,73,99` - browsers send "simple" cross-origin
  `POST` with `text/plain` to a local server without a preflight; requiring
  `Content-Type: application/json` (ignore params, case-insensitive) forces a
  preflight the server never grants.
- Impact: a web page the operator visits could POST commands to
  `localhost:8000/api/v1/commands` if any content type were accepted. CWE-352.
- Mitigation (testable): `415 unsupported_media_type` for missing /
  `text/plain` / `application/x-www-form-urlencoded`; `application/json`,
  `application/json; charset=utf-8`, `Application/JSON` accepted. DNS-rebinding /
  Host allow-listing is out of scope and recorded as such (`09-...:120`).

### [MEDIUM] T-68 Envelope/query DoS: full hardening limits must reach the scanner, not only `max_bytes` (DoS) - carries 01.0 T-01
- Subtask(s): 09 (07 for query).
- Vector / evidence: `09-...:74` sets `limits.max_bytes =
  config.max_request_body_bytes` and `limits.max_id_len` but does **not**
  mention `max_depth`/`max_members`/`max_key_len`; `parse_request` DoS caps
  (depth 8 / members 256 / key 128) live in `envelope_limits` defaults. Session
  `413` (`http_session.cpp:59`) bounds raw bytes but not nesting.
- Impact: if the handler zero-initializes a partial `envelope_limits` or
  overrides only two fields with a loose value, deep-nested JSON could bypass
  the depth/member caps on the only network ingress parser.
- Mitigation (testable): the handler MUST construct a full `envelope_limits`
  carrying the hardening defaults (depth 8, members 256, key 128) and override
  only `max_bytes`/`max_id_len`; the body is never parsed by anything but
  `parse_request`. For `GET /api/v1/links`, `parse_query_string` is iterative,
  bounded by `max_request_target_length` (2048), and rejects malformed/`%00`.
  Tests: a depth-9 body over `/api/v1/commands` -> `too_deep` (400
  `invalid_envelope`); a 65537-byte body -> 400 (session 413 covered
  separately); a 2 KiB query does not crash.

### [MEDIUM] T-73 Query-string parser on untrusted input (Tampering/DoS/injection)
- Subtask(s): 07.
- Vector / evidence: `07-...:57-61,94,112` - `parse_query_string`/`percent_decode`
  handle `%XX`, `+`, repeated keys; `%zz`/`%2`/trailing `%` -> `malformed_query`;
  `%00` (decoded NUL) -> error; empty name -> error; duplicate name -> 400
  `<name>: duplicate`.
- Impact: a malformed or NUL-bearing query reaching `args`/the registry could
  truncate downstream C-string handling, forge an args member, or crash.
- Mitigation (testable): all malformed-`%`, `%00`, empty-name, duplicate-name
  cases return `400` JSON (never 500/crash); integer params (`offset`,`limit`)
  only emitted as JSON numbers when `^[0-9]+$` (<=18 digits) else as a string so
  the registry reports `wrong_type`; every other/unknown name forwarded as a
  string so the registry reports `<name>: unknown`; decoded `q`/`tag`/`campaign`
  escaped by `args_builder` and length-bounded (256) by the registry. Tests:
  `20_query_params` hostile cases; `21_...` every bad param -> 400.

### [MEDIUM] T-62 Error/status mapping must be value-free and come only from the fixed table (Info disclosure) - carries 01.0 T-10/T-16
- Subtask(s): 02.
- Vector / evidence: `02-...:74-83,116,120` - `legacy_error_code` =
  01.0/02 `legacy_rest_code`, except `invalid_field` with message
  `invalid_timestamp`/`invalid_bucket` promoted to that code; statuses from
  `legacy_rest_status`; `resource_response` body via `makeApiErrorResponse`.
  C3 requires byte-identical legacy codes; the message must stay fixed/arg-name
  only.
- Impact: if the bridge forwarded `error.message` built from request values or
  an exception `what()`, the response/log could leak a target URL, path, SQL or
  DSN; a distinguishable malformed-vs-SSRF code would be an SSRF oracle (01.0
  T-16).
- Mitigation (testable): the only promoted details are the two fixed tokens;
  any other `invalid_field` message stays `invalid_request` and the message is a
  fixed string or arg name (never a value); `invalid_url` covers malformed and
  SSRF-blocked identically; a `job`-carrying response on a resource route -> 500
  `internal`. Test (`15_command_bridge`): every `CommandErrorCode` ->
  correct status+code; `invalid_timestamp`/`invalid_bucket` promoted,
  `slug: missing` **not** promoted; no response message contains an input value.

### [MEDIUM] T-65 Reverse-proxy on the same host makes every peer loopback, so `role=admin` grants admin to all (Elevation) - operator-docs mitigation
- Subtask(s): 08 (help text), 09 (behavior), Task 08.0 (docs).
- Vector / evidence: `08-...:77-78`; `09-...:121-122` - the peer is the TCP
  peer; behind a proxy on the same host every request is loopback;
  `X-Forwarded-For`/`Forwarded` are deliberately **not** honored (spoofable).
- Impact: an operator who runs `--command-api-role admin` behind a local reverse
  proxy unknowingly grants admin to every client of the proxy.
- Mitigation (testable): `--command-api-role` help text states (verbatim intent)
  that `admin` is honored only for loopback peers, that behind a same-host proxy
  every request is loopback so keep `user`, and that `X-Forwarded-For` is not
  honored; operator guide (08.0/07) repeats it. Test: `--help` output contains
  the warning (`cli__11_...`).

### [MEDIUM] T-70 Peer address plumbing must fail closed to `User` and never be logged as PII (Elevation, Info disclosure)
- Subtask(s): 09.
- Vector / evidence: `09-...:42-44,61-68` - `remote_endpoint(ec)`; on `ec` pass
  `std::nullopt`; `RouteContext::peer` default empty; "Not logged." The defaulted

- Impact: if a `remote_endpoint` error yielded a non-nullopt/garbage address, a

  handlers ignore `context.peer` (C10). Tests: `dispatch` carries the passed

### [MEDIUM] T-84 `principal`/`transport` reach audit verbatim and are not PII-redacted; adapters must use non-identifying labels (Info disclosure, Repudiation) - carries CF-3

### [MEDIUM] T-75 Public create (and `dry_run`) has no rate limit; the registry has no rate-limit hook (DoS) - SPEC GAP
- Subtask(s): 04, 09 (create paths); gate owner 08.
- Vector / evidence: state `milestone_carry_forward[19]`; `grep` confirms no
  `IRateLimiter`/rate-limit call in `link_handlers.cpp` today; subtask 04 (REST
  create) and 09 (`POST /api/v1/commands` -> `link.create`) add no throttle, and
  no 04.0 spec mentions rate limiting. `dry_run` create runs the full validator
  (SSRF resolution, normalization) on the request thread.
- Impact: an unauthenticated client can drive unbounded create / `dry_run`

- Mitigation (testable, decision required): record in spec 04 (and 09) that

  cheaper for SSRF/validator cost). If deferred, carry it forward with an owner
  and state that the config gate + body-size hardening are the only current
  bounds. Amend `04-rest-create-via-registry.md` and
  `09-rest-post-commands-endpoint.md` before implementation.

### [MEDIUM] T-76 `link.stats` span/bucket count is unbounded; the bucket-count cap owned by 04.0 is in no subtask spec (DoS) - SPEC GAP
- Subtask(s): 03 (REST stats adapter) + shared reader (03.0/08 `link.stats`).
- Vector / evidence: state `milestone_carry_forward[21]`; status.md USER
  2026-11-16 "cap the number of buckets ... fixed maximum e.g. 10,000 ...
  applies to REST `GET /api/v1/links/{slug}/stats` and `link.stats` alike. Owner
  Task 04.0". Subtask 03 re-points stats to `link.stats` but specifies **no**
  bucket cap (`03-...:23-24` only keeps `invalid_timestamp`/`invalid_bucket`).
  `LegacyLinkStatsReader::read` bounds only `from<to` and `bucket in

- Impact: a single unauthenticated `GET .../stats?from=0&to=9999999999&bucket=hour`
  allocates/serializes ~10^5 buckets; repeated calls are a memory/CPU amplifier.

- Mitigation (testable): amend spec 03 to own the cap for the REST stats adapter

### [LOW] T-72 `GET /api/v1/links` 100k-row scan per call under read (DoS amplifier) - carries 03.0 T-56

### [LOW] T-77 Secrets on the CLI command line are visible in process listings and shell history (Info disclosure)

- Vector / evidence: `13-...:68`; `12-...:72-73` - `cmd --arg k=v` and

### [LOW] T-78 CLI `--arg` coercion is injection-inert by construction (Tampering)

### [LOW] T-79 `--json`/stdin bounded; oversized input rejected without unbounded allocation (DoS)
