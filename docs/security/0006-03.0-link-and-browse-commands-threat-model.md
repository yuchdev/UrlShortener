# Threat Model - Milestone 0006 Task 03.0 Link and browse commands - 2026-11-14

Design-time (pre-implementation) STRIDE review of the 18 subtask specs in
`docs/roadmap/0006-unified-command-model-and-tui/03.0-link-and-browse-commands/`,
plan.md "Shared contracts" C1/C3/C6/C7/C10/C11, decision-log D1/D2/D10/D16, and the
code the task extends (`commands/*`, `app/*` `LinkCommandService`/`ILinkStore`,
storage ports `IMetadataRepository`/`IClickEventRepository`, `security/access_guard.hpp`).
No 03.0 product code exists yet; every requirement is phrased so an implementation
briefing and `testing-expert` can turn it into an assertion. T-IDs start at T-50 to
avoid colliding with 01.0 (T-01..T-22) and 02.0 (T-30..T-41).

Scope note: this task (a) extends the metadata/analytics ports with
filter/sort/page/count reads (`ListLinksPage`, `ListEvents`), (b) registers the nine
existing link commands as descriptors over `LinkCommandService` with byte-identical
REST bodies (C3), and (c) adds the new read surface the TUI/web clients need:
`link.list`, `db.tables`, `db.rows`, `system.info`. SSRF/URL validation, slug and
metadata validation and the error vocabulary stay in `LinkCommandService` upstream of
the store (02.0 T-40) and are reviewed here only as an invariant that must not regress.

## Assets & trust boundaries

- **Untrusted command envelope / args (primary boundary):** `table`, `sort`, `order`,
  `q`, `slug`, `id`, `status`, `offset`, `limit`, `target_url`, `tags`, `metadata`,
  `campaign`, `from`/`to`/`bucket`. Tokenized only by the 01.0 bounded scanner, decoded
  by `ArgsView`, bound-checked by `ArgSpec`, then handed to handlers -> services/ports.
- **`db.*` table allowlist (new exposure surface):** `TableCatalog` is the whole
  allowlist; a table that is not registered cannot be named, listed or read (C6). The
  backing physical tables are **never** queried by name - rows come through ports
  (`ILinkLister`, `IClickEventRepository::ListEvents`). The forbidden set
  (`app_users`, `auth_sessions`, `service_clients`, `auth_audit_log`,
  `user_credentials`) must be refused by `TableCatalog::add` even if someone writes an
  `ITableSource` for one.
- **Column projections (new exposure surface):** each `ITableSource` fixes a literal
  column list; the columns that exist are exactly the columns that may leave. `links`
  exposes no `owner`/`attributes`; `click_events` exposes `client_id_hash` and no other
  client identifier.
- **`system.info` output (new exposure surface):** backend **names** from a fixed
  allowlist plus an explicitly-named non-secret `ServerConfig` subset; never
  `postgres_dsn`/`redis_address`/`sqlite_path`/`tls`/`analytics_client_hash_salt`.
- **Audit sink / response envelope (sinks crossing back out):** must carry no argument
  values, no raw client ids, no driver/exception text; `audit_target` is a validated
  resource id only (01.0 T-15).
- **SQL built in `SqlClickEventRepository::ListEvents` (new query):** the only new SQL
  this task writes; every value must be a bound parameter and the only interpolated text
  is whitelisted column/direction literals chosen by `switch` over enums.
- **Secrets at risk:** DSNs, redis address, sqlite path, TLS material, analytics salt,
  raw client identifiers, driver `what()` text, hostile slugs/URLs reaching logs.

## Carried-in requirements (from 01.0 / 02.0 reviews)

- **R-A (01.0/08, T-21):** every `supports_dry_run` path must perform no mutation and
  bounded work on the request thread. Here `link.create`/`link.update` are `sync`
  (not jobs); dry_run routes to `ValidateCreateLink`/`ValidateUpdateLink`, which run the
  full validators but skip `store_.create/update/invalidateCache` (subtask 06). The four
  lifecycle commands set `supports_dry_run=false` so a `dry_run` request returns
  `unsupported` with no mutation (subtask 10). See T-57.
- **R-B (01.0/09):** `audit_target` must be a validated resource id (slug/id), never a
  raw argument value. See T-55.
- **R-C (01.0/09):** non-mutating commands and `unknown_command` are not audited. All
  four browse commands (`link.list`, `db.tables`, `db.rows`, `system.info`) and the three
  read link commands are `mutating=false` -> zero audit records; no audit-on-denial. See
  T-59 disposition.
- **R-D (01.0/11+12, T-19):** `register_documented_commands` / catalog dump binds the new
  descriptors to null services and must never invoke their handlers. See T-58.
- **R-E (carried from both reviews):** Postgres `ListLinks` owner filter returns 0 rows
  and the Postgres contract harness lacks per-case isolation - both must be owned by
  03.0/01-02. See T-50 (SPEC GAP).
- **R-F (02.0 T-35/R-5):** redirect/lookup collapses repository errors to not_found
  (404/410) rather than 5xx. See T-54.

## Findings

### [MEDIUM] T-50 Postgres ListLinks owner-filter defect and Postgres contract-harness per-case isolation are not owned by specs 01/02 (Integrity / test integrity) - SPEC GAP
- Subtask(s): 01, 02 (carried item R-E).
- Vector / evidence: `01-...:33-36` freezes `ISqlSession::List` and the default
  `ListLinksPage` (`01-...:94-98`) pages `ListLinks(base)` with `base.owner = query.owner`,
  so it inherits the existing untyped `:owner_id IS NULL` bind that returns 0 rows on
  Postgres (metadata__06 failure noted in the 03.0 README and carried from prior reviews).
  `02-...:69-74,98` adds an `owner` narrowing case to `11_list_page_flags_and_predicate`
  that runs on **every** backend including Postgres, and `02-...:26-27,88-90` resets only
  the shared **SQLite** file per `MakeMetadataHarnesses()` - no per-case isolation is
  specified for the Postgres harness. Neither spec mentions fixing the bind or isolating
  Postgres cases; `02-...:76` even says "fix the test, never the helper", which would mask
  a real backend defect.
- Impact: `ListLinksPage` (and therefore any future owner-scoped `link.list`) silently
  returns the wrong rows on Postgres; the new contract test 11 either fails on Postgres
  or is weakened to hide it; cross-case state bleed on a shared Postgres schema makes the
  new paging/total assertions flaky. In Milestone 0002 (multi-tenant, owner = tenant), a
  broken owner filter is a cross-tenant disclosure/hiding boundary.
- Mitigation (testable): amend spec 01 to fix the Postgres owner bind (typed/`CAST`ed
  `:owner_id` with a `has_owner` guard, mirroring 03.0/04's `(:has_* = 0 OR ...)` pattern)
  as part of the `ListLinks`/`ListLinksPage` rework, and amend spec 02 to (a) run the
  `owner` case on Postgres and assert it narrows correctly, and (b) give the Postgres
  contract harness per-case isolation (unique owner/slug prefixes or a per-case truncate),
  never weakening a case to make SQL pass. Resolve in the 01 and 02 specs before
  implementation.

### [MEDIUM] T-51 db.* table/sort/table-name reaching SQL or escaping the allowlist (Tampering / injection, Info disclosure)
- Subtask(s): 15, 16, 04.
- Vector / evidence: `15-...:97-102,131-134` (`table` arg selects a source by exact name
  via `catalog.find`; unknown -> `not_found` without echoing the name; `sort` rejected
  with `invalid_field` unless it is a `sortable` column); `16-...:80-85` (sources map the
  validated `sort` string to their own `list_sort`/`ClickEventSort` enum); `04-...:50-62`
  (`order_clause` returns one of three string literals chosen by `switch`; all filters
  bound as `(:has_* = 0 OR col = :p)`; `escape_like` escapes `\ % _`).
- Impact: if a source mapped an attacker-influenced `sort`/`table` string into SQL text,
  or `TableCatalog::add` admitted an auth table, `db.rows` would become a schema probe or
  a SQL-injection/row-exfiltration vector over `app_users`/`auth_sessions`/`service_clients`/
  `auth_audit_log`.
- Mitigation (testable): `TableCatalog::add` returns `false` for each of the five
  forbidden names and for malformed names (test enumerates them); `db.rows` for any
  unregistered name (`users`, `app_users`, `sqlite_master`, `information_schema.tables`,
  `links;--`, `../links`, `LINKS`) returns `not_found` and the response never contains the
  supplied name; `sort` not in a source's declared `sortable` columns -> `invalid_field`;
  each source's string->enum sort map is **exhaustive over its sortable columns with a safe
  default** (never a fall-through to an unintended column); `grep "SELECT\|FROM "
  src/commands src/app/table_catalog.cpp` is empty; subtask 04's injection strings in
  `slug`/`text` are inert and `click_events` survives. (Design is allowlist-by-construction;
  these are the regression guards that keep it that way - subtask 18 test 30.)

### [MEDIUM] T-52 click_events exposing a raw client identifier or unescaped free-text (Info disclosure, Tampering/log-or-JSON injection)
- Subtask(s): 03, 04, 16.
- Vector / evidence: `16-...:73-85,105-106` (`client_id_hash` is the only identifier
  column; `referrer`/`user_agent` are untrusted and must be `jsonString`-escaped);
  `03-...:30-31,113` (`ClickEvent` holds `client_id_hash` only - no raw id exists to leak);
  `04-...:62` (nullable text columns map `soci::i_null` to empty string).
- Impact: a non-hashed client identifier column, or an unescaped `referrer`/`user_agent`
  carrying `"`/`\`/newline/`<script>`, would leak PII or break the JSON/log the row is
  embedded in.
- Mitigation (testable): the `click_events` column list is a literal constant in the
  source, never derived from `ClickEvent` reflection or the repository result; the row
  key-set test fails if any key matches `ip`/`address`/`client_id`/`fingerprint`; a seeded
  event with `"`, `\`, newline and a script tag in `user_agent` stays valid JSON;
  `ListEvents` is never reached from `RedirectAnalyticsHook`/`AnalyticsWorker`
  (`grep` guard, `03-...:124`, `04-...:117`).

### [MEDIUM] T-53 system.info leaking a DSN / path / salt / TLS material (Info disclosure)
- Subtask(s): 17.
- Vector / evidence: `17-...:17-20,40,107-108,140-142` (emit backend **names** from a fixed
  allowlist; any value outside the allowlist becomes `"unknown"` so a DSN mis-set in a
  `backend` field cannot leak; `tls` and `analytics_client_hash_salt` are never read; the
  `shortener` block is an explicitly-named non-secret `ServerConfig` subset).
- Impact: passing `StorageConfig`/`ServerConfig` through without an allowlist would surface
  `postgres_dsn` (user:password@host), `redis_address`, `sqlite_path`, TLS cert/key paths
  and passphrase, or the analytics salt to any `read` caller (both roles).
- Mitigation (testable): the secret test (`17-...:133`) populates DSN/redis/path/`backend`
  with sentinel credentials and sets TLS + salt sentinels, and asserts the serialized JSON
  contains none of `SECRETPW`, `TOKEN`, the path, `postgres://`, `redis://`, `salt`, `@`,
  or the TLS/salt sentinels; unknown backend -> `"unknown"`;
  `grep "sqlite_path\|postgres_dsn\|redis_address" src/app/system_info.cpp` and
  `grep "\.tls\b\|analytics_client_hash_salt"` are empty. Requirement: any future
  `ServerConfig` field added to `ShortenerSettings` is a conscious allowlist decision,
  re-reviewed here; the struct must never gain `tls`/salt/network fields.

### [MEDIUM] T-54 Redirect/lookup outage-as-not-found (R-5) is owned by no 03.0 subtask (Availability / integrity) - CARRIED, NEEDS ADR
- Subtask(s): none in 03.0 (carried item R-F from 02.0 T-35).
- Vector / evidence: 02.0 `03-...` `findBySlug` returns `std::optional`, collapsing
  `transient/permanent_failure` to `nullopt` -> redirect handler emits 404/410, not 503.
  No 03.0 spec touches `findBySlug`/`LinkService::Resolve` (C10 holds them frozen). The
  **browse** read path does *not* inherit this defect: `ListLinksPage` and the listers
  surface `storage_failure` distinctly (`01-...:96-98`, `12-...:98-99`), and `ListEvents`
  surfaces `repository`/`storage_failure` (`03-...:81`, `16-...:83-85`) rather than an
  empty page.
- Impact: during a DB blip every redirect looks deleted/absent; an actor inducing
  repository errors makes all links vanish (availability/integrity only; no disclosure,
  no cache poisoning). Unchanged from 02.0.
- Mitigation: 03.0 keeps redirect parity (C10) and does **not** introduce a Result-carrying
  `findBySlug`; the new browse/list reads already carry `storage_failure` and must keep
  distinguishing it from an empty result (not collapsed to `not_found`/empty). A
  Result-carrying redirect lookup remains deferred and is **not** owned by any 03.0 subtask
  - it needs an ADR (redirect 5xx-vs-404 semantics on outage) before any subtask adopts it.
  Record the ADR requirement in the decision log. Test (browse side): a lister/repository
  forced into `permanent_failure` yields `storage_failure` with a fixed detail (never the
  driver message) and no partial/empty page is mistaken for success.

### [LOW] T-55 Mutating-command audit_target on failure is an addressed raw slug/id (Repudiation / log injection)
- Subtask(s): 05, 07, 09, 10 (carried item R-B).
- Vector / evidence: `05-...:57-60` (result wrappers take `audit_target` = "the slug/id the
  caller addressed ... used when the call fails; on success the view's own slug is used");
  `07-...:78` (`link_view_result(result, cmd.slug.value_or(""))`); `09-...:76`, `10-...:61`
  pass `cmd.slug`. On a failure outcome the audit record's `target` is the slug/id the
  caller sent, which has not been through service validation.
- Impact: a hostile or overlong slug/id becomes the audit `target` on a failed mutation,
  risking log-line forgery if the sink did not bound/sanitize it.
- Mitigation (testable): `audit_target` for the mutating commands is only the addressed
  slug/id - never `target_url`, `tags`, `metadata` or any other value (C6) - and relies on
  01.0/09 `audit_fields` capping `target` to 64 chars and stripping control characters
  (01.0 T-15, mitigated). On a generated-slug create the failure `audit_target` is empty,
  not a URL. Test: a `link.update` with a 300-char control-char slug that fails `not_found`
  produces an audit `target` <=64 chars with no control characters and no arg value other
  than the slug.

### [LOW] T-56 Unbounded O(n) full-scan browse under read permission (DoS amplifier)
- Subtask(s): 01, 12, 13, 14, 16.
- Vector / evidence: `01-...:94-98,154` (`ListLinksPage` scans up to `kListScanLimit=100000`
  records, decoding each, per call; overflow -> `permanent_failure`); `12-...:143-145`,
  `13-...:99` (O(n) decode per `link.list` call); `16-...:129`, `04-...:122` (`LIKE` is a
  sequential scan on `click_events`). All four browse commands are `Permission::read`, so
  `ControlSet::User` can call them.
- Impact: a `User` issuing repeated `link.list`/`db.rows` against a large store drives
  up-to-100k-row decode or a full `LIKE` scan per call - a CPU/IO amplifier. Never on the
  redirect fast path (C10); management-plane only.
- Mitigation (testable): the `kListScanLimit` cap is enforced and returns
  `permanent_failure`/`storage_failure` rather than truncating silently (`01-...:96`,
  test 02); `limit` is 1..500 and `offset>=0` on `link.list`/`db.rows` (rejected by
  ArgSpec before the lister/source runs); `q`/`text` is bounded (<=256). Accepted as an
  operator-tool cost (same disposition as 02.0 T-36); SQL push-down of `text`/`sort`/
  `COUNT(*)` is the deferred follow-up that would remove the scan.

### [LOW] T-57 dry_run of link.create/update must not mutate and must be bounded (Tampering)
- Subtask(s): 06, 07, 09 (carried item R-A, 01.0 T-21).
- Vector / evidence: `06-...:30-57,84-85` (`ValidateCreateLink`/`ValidateUpdateLink` reuse
  one `Impl(..., bool persist)` and skip `store_.create/update/invalidateCache` under
  `persist=false`); `07-...:77`, `09-...:74` route `context.dry_run` to the Validate
  variant; `10-...:30,49` keep lifecycle commands `supports_dry_run=false`.
- Impact: a dry_run path that still wrote, or that did unbounded work, would mutate
  production state for a "validate only" request or block the request thread.
- Mitigation (testable): a dry_run `link.create` leaves `FakeLinkStore::findBySlug` empty;
  a dry_run `link.update` leaves the stored link byte-identical; a forced store failure
  does **not** surface under dry_run (no write attempted); `dry_run:true` on each lifecycle
  command returns `unsupported` with the store unchanged. Work is bounded (same validators
  as the real path, no extra I/O).

### [LOW] T-58 Catalog generator / registry builder invoking the new descriptors' handlers (DoS, side effects)
- Subtask(s): 11, 14, 15, 17, 18 (carried item R-D, 01.0 T-19).
- Vector / evidence: `18-...:78-85` (`build_command_runtime` is the only registry builder
  and wires real services); `11-...`/`14-...`/`15-...`/`17-...` factories bind handlers to
  live services, but `register_documented_commands` (01.0/11-12) binds the same descriptors
  to **null** services for `command_catalog_dump`.
- Impact: if the dump tool or a drift test called `execute` on a null-service descriptor it
  would crash or touch storage during a docs build.
- Mitigation (testable): the dump/drift path renders descriptor metadata only and never
  calls `execute`; `build_command_runtime` is the only place that constructs services and
  it opens no listener/`uri.txt`/`UriMapSingleton` (C5); test 29 asserts the registry
  contains exactly the expected names and that handlers run only through `execute`.

### [LOW] T-59 click_events table reads a process-local in-memory repository (Info disclosure surface / correctness) - OPEN WIRING, PRODUCT DECISION
- Subtask(s): 16, 18.
- Vector / evidence: `16-...:27-34` (the server writes clicks to the process-global
  `analyticsClickRepository()`, an `InMemoryClickEventRepository`; no composition code
  builds a `SqlClickEventRepository` for the server, so CLI/TUI processes read their own
  empty in-memory repo); `18-...:77` wires `ClickEventsTableSource(analyticsClickRepository())`.
- Impact: not a disclosure escalation (the source exposes `client_id_hash` only regardless
  of instance), but `db.rows click_events` shows an empty table in CLI/TUI processes and the
  rows it does show come from whichever instance the composition root passes. A future switch
  to a shared/persistent click repository must re-confirm the hashed-only column list holds.
- Mitigation: accepted/flagged to the milestone owner (`16-...:124-127`); `db.rows` audit
  disposition unchanged (read, not audited). Requirement: whatever `IClickEventRepository&`
  the composition root hands over, the column list stays the literal `client_id_hash`-only
  set (T-52); a persistent click store is a separate product decision, not a silent change.

## Requirements by subtask (for implementation briefings)

  (one filter implementation); not used on request paths (T-56).
- **14:** `limit` 1..500 and `offset>=0` rejected by ArgSpec before the lister; `q` bounded 256;

- **16:** literal column lists (never reflection); `client_id_hash` only; escape free-text;

- **17:** allowlisted backend names only; never read tls/salt/dsn/path; secret test passes;

## Verdict: PASS_WITH_FOLLOWUP

No CRITICAL finding, so this is **not** a merge BLOCK. The browse surface is sound by
construction: `db.*` is allowlist-only with an explicit forbidden auth-table set and
port-backed rows (no physical table name reaches SQL), `click_events` exposes
`client_id_hash` only, `system.info` emits allowlisted backend names and an
explicitly-named non-secret config subset, the one new SQL query binds every value and
whitelists only `switch`-chosen column/direction literals, authorization is by descriptor
permission enforced in `execute` before validation (no 03.0 command uses a `permission_for`
hook), dry_run routes to non-mutating Validate variants, and result JSON comes from the
shared REST serializers (C3 parity gate). Required follow-ups before the owning subtasks
start:

1. **T-50 (MEDIUM, spec gap in subtasks 01 + 02):** own the Postgres `ListLinks` owner-bind
   fix in spec 01 and per-case Postgres contract isolation + a real (not weakened) owner
   assertion in spec 02. Resolve in those specs before implementation.
2. **T-54 (MEDIUM, carried R-F):** record that 03.0 keeps redirect parity (C10) and does
   **not** introduce a Result-carrying `findBySlug`; the browse reads already carry
   `storage_failure` distinctly. The redirect 5xx-vs-404-on-outage decision is owned by **no
   03.0 subtask** and needs an **ADR** before any subtask adopts it - add it to the decision log.
3. **T-53 / T-52 / T-51 (MEDIUM, guards):** the secret test (17), the click row key-set test
   (16), and the allowlist/injection regression (15/18 test 30) are the executable gates that
   keep C6 from drifting; hand their assertions to `testing-expert`.

Carried/accepted as designed: R-A/T-57 (dry_run non-mutating Validate variants), R-B/T-55
(audit_target = addressed slug/id, bounded by 01.0/09), R-C (non-mutating browse/read
commands not audited; no audit-on-denial because all browse commands are `read` and both
`ControlSet` roles hold read - revisit if 0002 adds a read-restricted role), R-D/T-58
(catalog generator renders metadata only), T-56 (O(n) scan is an accepted operator-tool
cost, SQL push-down deferred), T-59 (click-repository instance wiring is a flagged product
decision; hashed-only columns hold regardless).

Hand T-50 to the spec authors and `cpp-expert`; hand the T-54 ADR to `app-architect`; hand
every per-threat assertion to `testing-expert` for the `listing__`, `app__`, `commands__`,
`metadata__` and `storage__` suites.
