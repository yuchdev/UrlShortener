# Threat Model - Milestone 0006 Task 01.0 Command model core - 2026-11-14

Design-time (pre-implementation) STRIDE review of the 13 subtask specs in
`docs/roadmap/0006-unified-command-model-and-tui/01.0-command-model-core/`,
plan.md "Shared contracts" C1-C11, decision-log D3/D4/D16, ADR 0002, and the
`AccessGuard`/`ControlSet` the registry must use. No product code exists yet;
every requirement below is phrased so an implementation briefing and
`testing-expert` can turn it into an assertion.

Scope note: this reviews only the transport-agnostic core (`url_shortener::commands`).
The transport-facing guarantees of D4 (command API off by default, loopback-only
`admin`, `manage_users` never over REST) live in Task 04.0 adapters and are out
of scope here except as a trust assumption (T-11).

## Assets & trust boundaries

- **Untrusted input surface (primary boundary):** the request-envelope JSON
  text. It arrives from a REST body, a stdio NDJSON line, CLI `--json`, and the
  TUI, and is tokenized by the one sanctioned scanner (`commands/json_scan.hpp`,
  subtask 01) feeding `parse_request` (03) and `ArgsView`/`validate_args` (05).
  There is no JSON library (C9); the scanner is the only JSON tokenizer in
  product code, so its bounds and escape handling are the whole input-hardening
  perimeter.
- **`args_json` (raw text):** carried verbatim through the envelope, decoded by
  `ArgsView`, handed to handlers -> DTO -> services -> storage. May hold secrets
  (tokens, credentials passed as args to future commands) and SSRF targets.
- **`CallerContext{principal, control_set, transport}` (06):** supplied by the
  adapter and **fully trusted** by `execute` as the authorization root (C7).
  The registry has no transport-based restriction of its own.
- **Audit sink output (09)** and **response envelope (04):** sensitive sinks
  that cross back out to logs and to the client; must not carry argument values,
  secrets, exception internals (paths/SQL/DSN), or raw client identifiers (C6).
- **Secrets at risk:** DSNs, TLS keys, tokens, the analytics salt, exception
  `what()` text, and attacker-influenced slugs/ids reaching logs.

## Findings

### [HIGH] T-01 Unbounded / recursive parsing of hostile JSON (DoS, Tampering)
- Subtask(s): 01 (03, 05 inherit).
- Vector / evidence: `01-json-object-scanner.md:58-73,116-135` (`scan_limits`
  max_bytes 65536 / max_depth 8 / max_members 256 / max_key_len 128; iterative
  state machine).
- Impact: stack exhaustion or memory blow-up from deeply nested or huge input
  on the only ingress parser; ANR of the server/stdio loop.
- Mitigation (testable): scanner MUST be iterative with no recursive call to
  `scan_object`/`scan_array` and no `<regex>`; it MUST enforce `max_bytes` on
  entry and `max_depth`/`max_members`/`max_key_len` as encountered. Tests:
  1 MB of `[` returns `too_large` with no stack growth; depth 9 -> `too_deep`;
  257 members -> `too_many_members`; 129-char key -> `malformed`; every
  truncated prefix of a sample document never crashes and never returns `ok`.

### [HIGH] T-02 Error/validation messages reflecting attacker input (Info disclosure, log injection)
- Subtask(s): 01, 03, 05, 09.
- Vector / evidence: `01:72-73` fixed error vocabulary; `03:83-101,155`;
  `05:85-95` ("message names the key, truncated to 64 chars and stripped of
  control characters"); `02:160-163` (`message` never receives arg values).
- Impact: a crafted arg/key echoed into an error message or audit line injects
  CR/LF into logs or reflects a secret back to the caller.
- Mitigation (testable): all parser/validator error messages use the fixed
  vocabulary only; any field/key named in a message is truncated <=64 chars and
  has control characters stripped; no message contains any substring of the
  input. Test: feed a recognizable secret value plus a bad field and assert the
  message (and audit record) contain neither the value nor any control char.

### [MEDIUM] T-03 Invalid-UTF-8 / NUL bytes passing through the scanner to sinks (Info disclosure, Tampering)
- Subtask(s): 01, 05, 09.
- Vector / evidence: `01:205-213` ("invalid UTF-8 in raw strings is passed
  through ... not promised"); `05:112-114` checks embedded NUL only in decoded
  **string values**, not in **keys**; `09:94-97` audit sanitizes control
  characters only.
- Impact: invalid UTF-8 or embedded NUL in a key or value flows into storage,
  response, and the audit/JSON log; invalid bytes can corrupt log consumers and
  NUL can truncate downstream C-string handling.
- Mitigation (testable): `validate_args` MUST reject embedded NUL in decoded
  **keys** as well as values (`wrong_type`/`unknown`); `audit_fields` and any
  log sink MUST neutralize invalid UTF-8 bytes (not only control chars) before
  emission. Test: a `\u0000` in a key and a bare 0x80 byte in a value are
  rejected or escaped and never appear raw in the audit output.

### [HIGH] T-04 Envelope smuggling via duplicate / unknown / nested-look-alike keys (Tampering)
- Subtask(s): 01, 03.
- Vector / evidence: `01:157-178` (nested look-alike `{"args":{"command":"evil"},"command":"link.get"}`
  regression, duplicate-key rejection); `03:99-107` (unknown top-level key ->
  `invalid_envelope`, closed envelope in v1).
- Impact: the old `core/utils.hpp` first-occurrence search would let a nested
  `command`/`v` be read as top-level, or a duplicate key mean two things on two
  transports, defeating "identical command" and authorization decisions.
- Mitigation (testable): scanner enumerates only true top-level members; a
  duplicate top-level key -> `duplicate_key`; `parse_request` rejects any
  unknown top-level key and unknown `options` key -> `invalid_envelope`. Tests:
  the nested look-alike yields exactly two top-level members and
  `find_member("command")` is `link.get`; `{"foo":1}` and a duplicate key are
  rejected.

### [MEDIUM] T-05 Best-effort echoed `id` in error responses carries control chars / overlong (Info disclosure, log injection)
- Subtask(s): 03.
- Vector / evidence: `03:68-71,95-96,113-118` (parser extracts `id` first so an
  error response "can still echo a valid client id when another field is bad";
  `parse_request_result::id`).
- Impact: an envelope whose `id` is valid but another field is bad echoes `id`
  back into the response and audit; if the best-effort path adopts an
  unvalidated `id`, control chars/overlength reach the response and logs.
- Mitigation (testable): the id echoed in ANY response (including failure) MUST
  first pass the id rules (1..`max_id_len`, no control chars) or fall back to
  `next_server_id()`. Test: envelope with a control-char `id` plus a bad field
  produces an error whose echoed id is a `srv-<n>`, not the hostile id.

### [HIGH] T-06 ArgSpec caps not reconciled with scanner limits (DoS trade-off / C3 contract break) - SPEC GAP
- Subtask(s): 05 (interacts with 01; triggered by D10 in 03.0/07).
- Vector / evidence: `05:58-60` (`max_length` 2048, `max_items` 64; raised to
  65536/4096 for link commands by D10, decision-log:86,113); `01:59-64,96-99`
  (`scan_array`/`scan_object` default `max_members` 256, `max_bytes` 65536).
  Subtask 05 does not state which `scan_limits` `validate_args` passes to the
  nested `scan_array`/`scan_object`.
- Impact: if nested scans use defaults, a list arg with `max_items` 4096 is
  silently capped at 256 (`too_many_members`), rejecting bodies REST accepts
  today and breaking contract C3; if "fixed" by globally raising the scanner
  defaults, the top-level envelope member/byte DoS caps are relaxed for all
  input.
- Mitigation (testable): subtask 05 MUST specify that `validate_args` derives a
  per-arg `scan_limits` for nested `scan_array`/`scan_object` from that
  `ArgSpec`'s `max_items`/`max_length`, while the **top-level** envelope limits
  stay at the hardening defaults (`max_bytes` 65536, `max_members` 256). Test: a
  4096-item list arg validates, yet a 65537-byte envelope and a 257-member
  top-level object are still rejected.

### [MEDIUM] T-07 Numeric overflow / type confusion in integer args (Tampering)
- Subtask(s): 05.
- Vector / evidence: `05:100-101,143-144` (integer must be a JSON integer token
  fitting `long long`, within `[min,max]`).
- Impact: an out-of-range or float/string value accepted as an integer corrupts
  downstream limit/offset logic.
- Mitigation (testable): integer args accept only integer tokens (no
  fraction/exponent), fitting `long long`, within `[min,max]`. Test:
  `9223372036854775808`, `1.0`, `1e2`, `"5"`, `min-1`, `max+1` all rejected.

### [HIGH] T-08 Authorization-after-validation leaking schema / bypass (Elevation, Info disclosure)
- Subtask(s): 07.
- Vector / evidence: `07:53-73` pipeline order (base permission via `AccessGuard`
  is step 3, BEFORE `validate_args` step 4); `07:116-120` ("handler call count
  is 0 on denial"; "Denial precedes validation").
- Impact: if validation ran first, an unauthorized caller could probe the arg
  schema or trigger side effects before the permission gate.
- Mitigation (testable): `execute` performs base permission check before arg
  validation; on denial the handler is never entered. Tests: authorization
  matrix (`read`: Admin+User ok; `write`/`migrate`/`manage_users`: Admin only)
  with handler-call-count 0 on denial; an unauthorized caller with invalid args
  receives `not_authorized`, not `invalid_field`.

### [HIGH] T-09 `permission_for` hook lowering the required permission (Elevation)
- Subtask(s): 06, 07.
- Vector / evidence: `06:91-94` (hook "may only RAISE"); `07:67-73` (step 4a
  `p = max(base, hook(view))`, order `read<write<migrate<manage_users`,
  evaluated after validation on a validated view; D16).
- Impact: an argument-dependent hook that could lower the base permission (e.g.
  inline-vs-file `link.export`) would let a write action run under read.
- Mitigation (testable): effective permission = `max(base, hook)`; the hook is
  evaluated only after `ArgSpec` validation succeeds (never on an unvalidated
  view); a hook that would lower is ineffective. Tests: a `read` descriptor
  whose hook returns `write` when `path` present -> User with `path` is
  `not_authorized` and handler not called, Admin with `path` ok; a `write`
  descriptor whose hook returns `read` still requires `write`; a hook that
  throws -> `internal`.

### [HIGH] T-10 Exception text (paths, SQL, DSN) leaking through the error message (Info disclosure)
- Subtask(s): 07 (08 same isolation for factory/submitter/body).
- Vector / evidence: `07:78-82` ("never `e.what()`: it may contain paths or
  SQL"); `08:135` (factory/submitter exception -> `internal`).
- Impact: a handler/factory exception surfacing `what()` reveals filesystem
  paths, SQL, or a DSN to the caller.
- Mitigation (testable): every handler/factory/submitter call is wrapped in
  `catch(const std::exception&)` and `catch(...)` mapping to `internal` with the
  fixed message `internal error`; `e.what()` is never serialized. Test: a
  handler throwing `std::runtime_error("secret-dsn")` and one throwing an `int`
  both yield `internal` whose output contains neither `secret-dsn` nor any path.

### [MEDIUM] T-11 Registry authorizes solely on `CallerContext.control_set` (Spoofing/Elevation trust assumption)
- Subtask(s): 06, 07.
- Vector / evidence: `06:44-50` (`CallerContext` is adapter-supplied); `07:60-66`
  (guard built from `caller.control_set`). D4/C7 restrictions (loopback-only
  `admin`, `manage_users` never over REST) are not enforced in the core.
- Impact: a buggy or malicious adapter that sets `control_set = Admin` for a
  remote peer gets full write access; the core offers no defense in depth.
- Mitigation (testable): document in `command_registry.hpp` that `execute`
  trusts `control_set` as the sole authorization root and performs no
  transport-based restriction; the D4 guarantees MUST be enforced and tested in
  Task 04.0 (04.0/08, 04.0/09) and must not be assumed present here. Test (04.0,
  cross-referenced): a non-loopback peer never executes with `Admin` and
  `manage_users` is always refused over REST.

### [HIGH] T-12 Job factory/body running before authorization, or body reading freed request memory (Elevation, Info disclosure, UAF)
- Subtask(s): 06, 08.
- Vector / evidence: `08:77-94` (step 5 runs after steps 3+4a; no submitter ->
  `unsupported`, factory not called; "either returns a job or an error, never
  both"); `06:87-90` ("ArgsView is non-owning: the factory must COPY every value
  it needs into the body").
- Impact: a factory invoked before authorization would open files / do work for
  an unauthorized caller; a body holding the non-owning `ArgsView` after the
  request buffer is freed reads freed memory, potentially emitting another
  request's bytes into job results.
- Mitigation (testable): `job_factory` is invoked only after base permission,
  arg validation and `permission_for` pass; the body is self-contained (factory
  deep-copies every value); with no submitter set, no code path creates a job.
  Tests: unauthorized `async` request -> `not_authorized`, factory+submitter not
  called; invalid args -> `invalid_field`, factory not called; destroying the
  request buffer after `execute` does not change the body the fake submitter
  received; no-submitter + job descriptor -> `unsupported`, factory not called.

### [MEDIUM] T-13 `args_digest` / job record exposing raw args or secrets (Info disclosure, Repudiation)
- Subtask(s): 08 (09 for audit).
- Vector / evidence: `08:68-70` (`args_digest` = first 16 hex of
  `SHA-256(args_json)`); ADR 0002:165-170 job record holds `args_digest`, not
  raw args.
- Impact: if the job record or audit stored raw `args_json`, secrets passed as
  args would be persisted and readable via `job.get`.
- Mitigation (testable): the job record and audit carry only `args_digest`
  (truncated SHA-256) and the command name, never raw `args_json`; no arg value
  is copied into any job/audit field. Test: a secret-looking arg value appears
  nowhere in the submitted job metadata or the audit record.

### [MEDIUM] T-14 Missing, duplicated, or silently-lost audit for mutating actions (Repudiation)
- Subtask(s): 09.
- Vector / evidence: `09:80-97,106-108` (one record per attempted execution of a
  mutating command, including denials; sink is `noexcept`, wrapped in
  `try/catch`).
- Impact: without a one-per-execution guarantee, mutations on production data
  are unlogged or double-logged; a throwing sink could otherwise alter the
  response.
- Mitigation (testable): exactly one audit record per execution of a mutating
  command that reached a descriptor (success, denial, invalid_field,
  unsupported, busy, job_accepted, internal); non-mutating and unknown commands
  emit zero; audit failure never changes the response. Test: record count ==
  execution count across all listed outcomes; read-only and unknown commands
  produce zero records.

### [MEDIUM] T-15 Log injection via audit fields (Info disclosure, Tampering)
- Subtask(s): 09.
- Vector / evidence: `09:49-51,94-97` (`target` capped 64; `audit_fields`
  truncates every field to 128 and replaces control chars).
- Impact: an attacker-influenced slug/principal containing CR/LF/ESC forges or
  splits audit log lines.
- Mitigation (testable): `audit_fields` truncates every field to 128 chars and
  replaces control characters; `target` is a validated slug/id only, capped 64.
  Test: 300-char principal truncated to 128; newline and ESC sanitized.

### [MEDIUM] T-16 Error-code mapping leaking internal state or acting as an SSRF oracle (Info disclosure)
- Subtask(s): 02.
- Vector / evidence: `docs/commands/README.md` section 1 (`invalid_url` =
  "malformed **or** blocked (SSRF); intentionally indistinguishable");
  `02:76-96` single table; `02:160-163` message never carries arg values.
- Impact: distinguishing "malformed URL" from "blocked private target" turns the
  create path into an SSRF probe for internal network layout.
- Mitigation (testable): `invalid_url` covers both malformed and SSRF-blocked
  targets with the same code/status and a value-free message; statuses/exit
  codes come only from the one table. Test: a malformed URL and a private-target
  URL both yield `invalid_url` with identical status and a message free of the
  input.

### [MEDIUM] T-17 Malformed / injected `result_json` breaking the response envelope (Tampering)
- Subtask(s): 04 (07 for the empty-result guard).
- Vector / evidence: `04:85-92` (`result_json` embedded verbatim, not
  re-escaped; invariant violation -> `internal` envelope; cheap first-char
  sanity check); `07:82-83` (empty `result_json` -> `internal`).
- Impact: a handler that concatenates untrusted input into `result_json` can
  inject fields or break the envelope JSON seen by clients/stdio consumers.
- Mitigation (testable): `serialize_response` escapes `id`/`message` via
  `jsonString`, embeds `result_json` verbatim only after the first-char sanity
  check, and returns a well-formed `internal` envelope on any invariant
  violation; handlers (Task 03.0) MUST build `result_json` via the trusted
  serializers, never by concatenating untrusted input. Test: invariant
  violations never produce malformed JSON; an embedded quote/brace/unicode
  result is not re-escaped and round-trips.

### [MEDIUM] T-18 Transport/storage code bypassing the registry via include leakage (Elevation, Tampering)
- Subtask(s): 13.
- Vector / evidence: `13:92-99` forbidden-include list
  (`boost/beast`, `boost/asio`, `boost/program_options`, `ftxui`,
  `url_shortener/http/`, `/storage/`, `/composition/`, `/cli/`, `/tui/`,
  `core/utils.hpp`, `<regex>`).
- Impact: a commands header pulling in storage/http types invites a transport to
  reach storage directly, bypassing authorization/validation (defeating C1/C7).
- Mitigation (testable): the hygiene test fails on any forbidden include in
  `include/url_shortener/commands/`; a negative self-test proves the checker
  catches `boost/beast`. Documented limitation: the check is textual and cannot
  see transitive includes, compensated by banning `core/utils.hpp` (which pulls
  Beast) outright.

### [LOW] T-19 Catalog generator invoking null-service handlers / executing commands (DoS, side effects)
- Subtask(s): 11, 12.
- Vector / evidence: `12:66-69,121-129` (`register_documented_commands` binds
  handlers to null services "they must never be invoked by the generator"; tool
  "must not construct services, open files other than stdout, or touch
  storage").
- Impact: if the dump tool or drift test called `execute`, a null-service
  handler would crash or cause side effects during a docs build.
- Mitigation (testable): the dump tool and drift test render descriptor metadata
  only (`render_catalog_markdown`) and never call `execute`; the tool opens only
  stdout and constructs no services. Test: generator output is byte-identical
  across two runs with no I/O beyond stdout.

### [LOW] T-20 `command.list` advertising every command schema to any read caller (Info disclosure)
- Subtask(s): 10.
- Vector / evidence: `10:117-119` ("list shows what exists; execution is what is
  gated"; a `User` is not filtered).
- Impact: future `manage_users`/privileged command names and schemas are visible
  to unauthorized readers.
- Mitigation (testable): accepted design for this milestone (no `manage_users`
  commands exist yet); `command.list` serializes no handler, `maps_to`, or
  internal fields. Requirement: when Task 0002 adds `manage_users` descriptors,
  revisit permission-filtered listing. Test: output exposes only the catalog
  shape (`name,summary,perm,kind,mutating,dry_run,args`).

### [MEDIUM] T-21 dry_run of a job command runs the body synchronously on the caller thread (DoS, Tampering)
- Subtask(s): 08.
- Vector / evidence: `08:83-85` (dry_run + `kind==job` -> `job_factory` then body
  "runs **synchronously** on the caller thread with a no-op `IJobContext`").
- Impact: a mutating or unbounded body executed under dry_run blocks the request
  thread or performs writes the dry_run contract forbids; the registry cannot
  enforce "handler must not mutate".
- Mitigation (testable): the registry passes `ctx.dry_run = true` and creates no
  job; `supports_dry_run` handlers/factories (Task 03.0) MUST be unit-tested to
  perform no mutation and bounded work under dry_run. Test (here): dry_run of a
  job descriptor returns a `result`, creates no job, and the fake factory sees
  `dry_run == true`; (03.0): a dry_run mutating handler leaves state unchanged.

## Verdict: PASS_WITH_FOLLOWUP

No CRITICAL finding, so this is not a merge BLOCK. The design is sound: the
single bounded scanner is the only tokenizer, authorization precedes validation,
error/audit text is value-free and control-char-sanitized, exceptions are
isolated to `internal`, and job records/audit carry only digests. Required
follow-ups before the owning subtasks start:

1. **T-06 (HIGH, spec gap in subtask 05):** specify how `validate_args` threads
   `scan_limits` into nested `scan_array`/`scan_object` so D10's raised per-arg
   caps work without relaxing the top-level envelope DoS caps. Resolve in the 05
   spec before implementation.
2. **T-05 (MEDIUM):** pin in the 03 spec that the best-effort echoed `id` is
   re-validated (length + no control chars) or falls back to `srv-<n>`.
3. **T-03 (MEDIUM):** add NUL-in-keys rejection to 05 and invalid-UTF-8
   neutralization to the 09 audit/log sink.

Hand fixes/clarifications for items 1-3 to `cpp-expert` (and the owning spec
authors); hand the per-threat assertions to `testing-expert` for the
`commands__*` unit suite.
